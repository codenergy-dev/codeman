# Secrets

The workflow is [`templates/codeman.yml`](../../templates/codeman.yml), which runs each task's jobs (`open-key`, `agent`, `close-key`, `apply`, `release-pod`) in [`templates/codeman-task.yml`](../../templates/codeman-task.yml); the jobs are described in [runs and jobs](../runs/runs-and-jobs.md#jobs). `codeman.yml` passes that workflow its secrets by name, and grants it at most the `agent` job's permissions plus `id-token: write`, which only the jobs that use Codeman's [backend](../backend/backend.md) ask for; each of its jobs references only the secrets the table below names, and asks for its own permissions.

| Secret | Used by | Safe | Why | Gap | Mitigation |
| --- | --- | --- | --- | --- | --- |
| `CODEMAN_GITHUB_APP_PRIVATE_KEY`, and the App tokens made from it | `select`, `apply` | Yes | These jobs run no LLM and no repository code. Each requests a token with only the permissions it needs. `apply` treats the agent's result as untrusted and filters it through the [change policy](../runs/changes.md#change-policy). The token that may write workflows is requested only to move workflows a maintainer accepted. | The App may write to every branch of the repositories it is installed on. Codeman only writes to task branches, but nothing else stops it. | Install the App on selected repositories only. Add a ruleset on the default branch that requires a pull request. |
| `CODEMAN_OPENROUTER_MANAGEMENT_KEY` | `open-key`, `close-key` | Yes | These jobs check out nothing, run no LLM and only call OpenRouter. | None known. | — |
| `CODEMAN_RUNPOD_API_KEY` (the `runpod-pod` and `runpod-serverless` providers) | `open-key`, `close-key`, `release-pod` | Yes | These jobs check out nothing, run no LLM and only call Runpod and the pods' gateways. Pods get only the hash of their admin token, derived from this key. | It may do anything in the Runpod account, including spend all its credits. | An account dedicated to Codeman, with prepaid credits and no auto-pay ([installation](../installation/runpod.md)). |
| `CODEMAN_RUNPOD_SERVERLESS_KEY` (the `runpod-serverless` provider) | Codeman's step in `agent`, which runs the gateway | Yes, with the `agent` job as the template has it | The same isolation as the encryption secret: the agent gets only a local URL and the run's token, which stops working when the run ends or its budget is spent. | It does not expire and has no spending limit. A step added to `agent` that runs repository code can read it ([risk 3](risks.md#3-steps-added-to-the-agent-job-run-outside-the-sandbox)), and run the endpoint at the account's cost until someone revokes it. | Restrict it to the endpoint; keep the endpoint at one worker; prepaid credits. If a step did run repository code, revoke the key. |
| `CODEMAN_OPENROUTER_KEY_ENCRYPTION_SECRET` | `open-key`, `agent` | Yes, with the `agent` job as the template has it | In `agent`, only Codeman's own step holds it. The agent runs as another user, which cannot read that step's process. See [agent sandbox](../runs/agent.md#agent-sandbox). | A step added to `agent` that runs repository code runs as the runner's user and can read it ([risk 3](risks.md#3-steps-added-to-the-agent-job-run-outside-the-sandbox)). With it, anyone can decrypt the task keys in the run logs, which are public on public repositories. | Run no repository code in `agent`. If a step did, rotate the secret. Each key it protects is disabled when its run ends and expires within 24 hours. |
| The run's task key, or its token for a self-hosted gateway | The agent, in `agent` | Partly | It is the agent's own credential. Its limit is what remains of the task's budget. `close-key` disables it (or ends the run on its gateway) when the run ends; a key expires after 24 hours, a pod's run once its budget is spent. On a pod that several tasks share, of any repository of the organization, it opens only its own run. It is masked in the logs, and it travels between jobs encrypted. See [budget](../budget/budget.md) and [OpenRouter](../inference/openrouter.md). | A manipulated agent can send it out ([risk 4](risks.md#4-the-agent-can-send-its-task-key-out)). | Keep the task budget low. [Roadmap](overview.md#roadmap) item 1. |
| `GITHUB_TOKEN` of `agent` (contents and actions read) | Codeman's step in `agent`, to download the results of workflows | Yes | The same isolation as the encryption secret. It can only read. | The same as the encryption secret. | The same as the encryption secret. |
| GitHub's OIDC token, and the backend's tokens made from it (`id-token: write`) | `select`, `open-key`, `close-key`, `release-pod` | Yes | These jobs run no LLM and no repository code. No key is stored: the OIDC token proves the job's repository and workflow, and Google exchanges it for an hour's access as the backend's service account, to Firestore only. The provider's attribute condition admits only the organization's repositories, by its ID, from `codeman.yml` on the default branch. Both tokens are masked. `agent` never gets one, so neither the agent nor a Serverless gateway reaches the backend. See [backend](../backend/backend.md). | Whoever can change `codeman.yml` or `codeman-task.yml` on the default branch can read and write all of the project's Firestore data, which holds Codeman's records but no secret (the pod registry holds each pod's nonce, from which only the GPU account key derives its admin token), and so can make other repositories' pods end or take new tasks; the condition cannot tell one job of the workflow from another, so `id-token: write` given to `agent` would let the agent in. | A Firebase project for Codeman only; the attribute condition of [installation](../installation/setup.md#4-set-up-the-backend); reviewed pull requests on the default branch; never give `agent` that permission. |
| `GITHUB_TOKEN` of `forward-review` and `next-run` (actions write) | These jobs | Yes | They only start the Codeman workflow with `gh workflow run`. They check out nothing, and values reach the command through environment variables, not the script. | None known. | — |
| The repository's own secrets, used by its other workflows | The repository's workflows. Codeman never reads them. | Depends on those workflows | Codeman does not reference them. | Workflows that run on Codeman's branches run code the agent wrote, with the secrets those workflows expose ([risk 1](risks.md#1-code-the-agent-wrote-runs-with-the-repositorys-secrets)). | See risk 1. |

Organization secrets whose visibility is limited to selected repositories stay limited to those repositories. Inside each of them, though, every workflow that references them gets them, on any branch, including Codeman's task branches.

Variables are not secrets. The backend's variables (`CODEMAN_FIREBASE_PROJECT`, `CODEMAN_WORKLOAD_IDENTITY_PROVIDER`, `CODEMAN_SERVICE_ACCOUNT`) name the project and the identity, and grant nothing without a job's OIDC token that the provider admits. `CODEMAN_SETTINGS`, the organization's [shared settings](../installation/shared-settings.md), is plain text: every repository it is shared with can read it, in any workflow, and the `select` job prints it and the values it gives in its log, which is public on public repositories. Settings never hold secrets; never put one in this variable. Whoever can change it changes the settings of every repository it is shared with, budgets and model included: only organization owners can, and each repository's `.codeman/settings.yml` still overrides it.
