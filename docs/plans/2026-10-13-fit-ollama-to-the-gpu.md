# Fit Ollama to the GPU

## Goal

A pod's model always runs whole on the GPU, or the pod's start fails saying why and what to change. Without Ollama settings that say otherwise, a pod serves as many requests at once as its profile's tasks, with the largest context that fits the GPU for them, from 64000 tokens up to the model's own; the result is cached, so later pods on the same settings skip the search.

## Context

- **Today.** A pod's gateway pulls the model and restarts Ollama with `OLLAMA_CONTEXT_LENGTH` set to the model's own context length, which may be 256k tokens or more, unless the `ollama` settings give `context-length` (`prepareOllama` in `src/gateway/pod.ts`). `num-parallel` is 1 unless the settings give it, whatever the profile's count. Nothing checks where Ollama put the model.
- **What Ollama 0.35.1 does** (the pod image's version), from its source at the tag and llama.cpp's at the tag Ollama pins, recorded in step 1:
  - Ollama runs llama.cpp's `llama-server`, tag `b11232` ([LLAMA_CPP_VERSION at v0.35.1](../web/ollama/llama-cpp-version-at-v0-35-1.md)). It always passes `-c` with the context length times the parallel requests, and `-np` with the parallel requests ([llm/llama_server.go](../web/ollama/llm-llama-server-go-at-v0-35-1.md#how-llama-server-starts)).
  - llama.cpp's fit (`--fit`, on by default) changes only the parameters left unset, and the context "if and only if equal to 0" ([common/fit.h](../web/llama-cpp/common-fit-h-at-b11232.md)). Since Ollama always sets `-c`, the fit never lowers the context: it lowers the layers on the GPU instead, and puts the rest on the CPU ([common/fit.cpp](../web/llama-cpp/common-fit-cpp-at-b11232.md)). That is the silent slowdown. `LLAMA_ARG_FIT_TARGET` is the fit's margin of free memory per GPU, 1024 MiB by default ([common/arg.cpp](../web/llama-cpp/common-arg-cpp-at-b11232.md), [common/common.h](../web/llama-cpp/common-common-h-at-b11232.md)); it decides GPU layers, never the context. So Ollama does not fit the context to the GPU, and Codeman must.
  - Without `OLLAMA_CONTEXT_LENGTH`, Ollama's context is a tier of the GPUs' total memory, set once at its start: 262144 tokens from 47 GiB, 32768 from 23 GiB, else 4096. It does not account for the model nor for `num_parallel`. Only that automatic context is ever lowered, once, after a load fails for memory, and coarsely (to 32768, then 4096); a load that falls back to the CPU does not fail ([server/routes.go](../web/ollama/server-routes-go-at-v0-35-1.md#the-default-context-length), [server/sched.go](../web/ollama/server-sched-go-at-v0-35-1.md#loading)).
  - `GET /api/ps` reports each loaded model's `size`, `size_vram` and `context_length` ([list running models](../web/ollama/list-running-models.md)). `size` equals `size_vram` exactly when every layer is on the GPU; `context_length` is one request's, not multiplied by the parallel requests ([llm/llama_server.go](../web/ollama/llm-llama-server-go-at-v0-35-1.md#what-it-reports), [server/sched.go](../web/ollama/server-sched-go-at-v0-35-1.md#what-apips-reports)). `GET /api/tags` gives a model's `size` on disk and `digest` ([list models](../web/ollama/list-models.md)). No route reports the GPUs.
  - Ollama serves models of some families one request at a time, whatever `OLLAMA_NUM_PARALLEL` says: `qwen35`, `qwen35moe`, `qwen3next`, `qwen3vl`, `qwen3vlmoe`, `mllama`, `lfm2`, `lfm2moe` and the `nemotron_h` ones ([server/sched.go](../web/ollama/server-sched-go-at-v0-35-1.md#parallel-requests)). The test repository's model must be checked against it: on such a family, its 4 tasks queue on one pod.
- **The image.** This changes `dist/gateway.js`. The image of the Ollama settings plan was never published, so one new image covers both plans. The pinned image (`POD_IMAGE`, `sha256:3252d4…`) cannot apply Ollama settings, and is listed in `IMAGES_WITHOUT_OLLAMA_SETTINGS`.
- **Constraints.** No new dependency. Firestore holds no secrets. Only the key jobs reach Firestore; the pod's gateway does not. The workflow's permissions do not change. Pods without Ollama settings on the pinned image keep their settings key.

## Decisions

Answered by the responsible person on 2026-10-13.

1. **Detecting a model not wholly on the GPU.** Options: (a) a warning in the log; (b) the pod's start fails, with a clear message; (c) nothing, as today.

   **Answer:** (b), always, an explicit `context-length` included. After loading the model, the gateway reads `GET /api/ps`; if any of it is off the GPU, the pod's start fails with a message such as "the model did not fit the GPU with 4 parallel requests and a context of 65536; lower `context-length` or use `kv-cache-type: q8_0`".

2. **`num-parallel` by default.** Options: (a) Ollama's default, 1; (b) the profile's task count.

   **Answer:** (b). Without `ollama: num-parallel`, it is the most tasks the profile serves in a run (`tasks`, or `max-tasks`; choice 5 settles the rest). An explicit `num-parallel` wins. More concurrent requests, as from other repositories' tasks on the same pod, queue in Ollama without error. The derived value is part of the pod's settings key, like an explicit one.

3. **`context-length` by default.** Options: (a) the model's own, as today; (b) a formula from the model's architecture and the GPU's memory; (c) asking Ollama: an estimate from the formula, then loads checked with `/api/ps`.

   **Answer:** (c). Without `context-length`, the gateway computes the largest context that fits for the parallel requests: a first estimate from the model's architecture (`/api/show`'s `model_info`: layers, K/V heads, key and value lengths), its weights and the GPU's memory; a load with it, checked with `/api/ps`; if not wholly on the GPU, a binary search down, in multiples of 4096, keeping a margin of GPU memory for runtime growth. The floor is 64000 tokens, which Ollama's docs recommend at least for agents and coding tools ([context length](../web/ollama/context-length.md)): if that does not fit with the parallel requests, the pod's start fails saying what to do (fewer tasks in the profile, a bigger GPU, or `kv-cache-type: q8_0`). The agent is told the computed context, not the model's own, so OpenCode compacts in time.

4. **Caching the result.** Options: (a) none: every pod searches; (b) in Firestore, keyed by what changes the memory.

   **Answer:** (b). Keyed by image, model (by digest when known), GPU type, `num-parallel`, K/V cache type and any other Ollama setting that changes memory, so later pods on the same combination skip the search. Firestore holds no secrets. Which job reads and writes it is choice 9.

### Choices made while writing the plan

Settled conservatively, within the decisions above.

5. **The most tasks a profile serves.** As the picker derives a run's cap ([profiles](../settings/profiles.md#how-many-tasks-a-run-takes)): `tasks: N` gives N; `max-tasks: M`, with or without `min-tasks`, gives M; `min-tasks` alone, and a profile without counts, give the run's cap, the largest `tasks` or `max-tasks` of the profiles, or 10 when some profile has `min-tasks` alone (so `min-tasks` alone gives 10); the top level gives the run's cap too, which is 1 with no count anywhere. `select` resolves it with the run's profile, and the `inference` choice carries it as `parallel`.
6. **Older images.** The derived `num-parallel`, the computed context, the cache and the GPU check apply only on images that can apply Ollama settings: an image of `IMAGES_WITHOUT_OLLAMA_SETTINGS`, the pinned one included, gets none of them, so its pods keep their settings key and serve exactly as today, and `open-key` logs once that they do not apply. Until the new image is pinned, nothing changes for runs without `ollama:`, and runs with it still stop before any pod, as now. Any other image (a new one, or one of `pod-image`) must report the fit in its gateway's status: a gateway that applies the Ollama settings but does not report a fit, such as one built between the two plans, fails the run like one that does not apply the settings, and the error says to list its image.
7. **The margin.** The fit's own margin, llama.cpp's `LLAMA_ARG_FIT_TARGET`, 1024 MiB per GPU by default, which the gateway leaves as it is: a model wholly on the GPU means the fit projected at least that much free. Setting the variable would also turn off Ollama's own allowance for a vision projector ([llm/llama_server.go](../web/ollama/llm-llama-server-go-at-v0-35-1.md#how-llama-server-starts)). The estimate subtracts it too, and `OLLAMA_GPU_OVERHEAD` when set.
8. **The search.** Contexts tried: the floor, the multiples of 4096 above it, and the model's own context, the largest. The floor is 64000, or the model's own when smaller; without the model's own context length, the gateway serves the floor, checked. It starts with the cached context (choice 9) when its model's digest matches, else with the estimate (choice 10); a start that fits is kept, as decided. Otherwise it searches the contexts below the start: a context that fits raises the lower bound, one that does not lowers the upper bound. Each try restarts Ollama with `OLLAMA_CONTEXT_LENGTH` set and loads the model, so nothing else holds the GPU. The served context is loaded last and checked again. At most about 8 loads for a model of 256k tokens.
9. **The cache.** A document per combination, `organizations/{owner}/contexts/{key}`, the key a hash of the image, the model's name, the GPU type and every Ollama variable of the pod except `OLLAMA_CONTEXT_LENGTH` (the cache applies only without it). Its fields: `image`, `model`, `digest`, `gpuType`, `ollama` (the variables), `contextLength`, `modelContextLength`, `parallel` (what Ollama serves), `loads`, `pod`, `recordedAt`. `open-key` reads and writes it, since the gateway has no access to Firestore: the task that creates a pod reads it first, and gives the pod the context and its digest (`CODEMAN_FIT`); the gateway uses it only when the pulled model's digest matches, and checks it like any other. Once the pod serves, the same `open-key` writes what the gateway found, when it found it by searching. A failed read or write is a warning: the pod searches. One more read per pod created, and one more write per search.
10. **The estimate.** Free memory: the GPU's memory less the model's size on disk, the margin and `OLLAMA_GPU_OVERHEAD`; divided by the K/V cache per token (layers with attention × K/V heads × (key length + value length) × the bytes of the cache type: 2 for `f16`, 34/32 for `q8_0`, 18/32 for `q4_0`) times the parallel requests Ollama serves; rounded down to a multiple of 4096, within the floor and the model's own. Layers with attention: `head_count_kv` summed when it is a list per layer; `block_count` divided by `full_attention_interval` when the model has it. It counts no compute buffers, so it errs high, which the search corrects. Where it would err low, with a `sliding_window`, or where a field is missing, there is no estimate, and the search starts at the model's own. The GPU's memory is Runpod's for the GPU type (`memory`, [get a GPU type](../web/runpod/get-a-gpu-type.md)), which `open-key` gives the pod as `CODEMAN_GPU_MEMORY_GB`.
11. **Parallel requests Ollama ignores.** When the model's family (`/api/show`'s `details.family`) is one Ollama 0.35.1 serves one request at a time, the gateway fits for 1, logs a warning, and reports it; `open-key` warns that the runs on the pod wait for each other's requests. The list lives beside `OLLAMA_VERSION` in `src/inference/ollama.ts`, checked against the recorded source like the variables.
12. **Failing a start.** A gateway whose start fails keeps answering for 2 minutes before it terminates the pod: `/health` says only that it failed, and `/admin/status`, which takes the admin token, gives the message. `open-key` reads it while it waits for the pod, fails the run with it, and terminates the pod as today. A task that joined the failing pod fails too, without creating another pod for the same settings, since they would fail the same way.
13. **Messages.** With an explicit `context-length`: "`<model>` does not fit the GPU with 4 parallel requests and a context of 65536 tokens: Ollama put 3.2 of its 61.0 GB off the GPU, which runs much slower. Lower `context-length` or `num-parallel` in the `ollama` settings, set `kv-cache-type: q8_0`, or use a GPU with more memory." Below the floor: "`<model>` does not fit the GPU with 4 parallel requests and a context of 64000 tokens, the least Codeman gives an agent: Ollama put … off the GPU. Give the profile fewer tasks (`tasks` or `max-tasks`) or set a smaller `num-parallel`, set `kv-cache-type: q8_0` in the `ollama` settings, or use a GPU with more memory." Both reach `open-key`'s log, as the reason the pod did not serve.
14. **What the gateway reports.** `/admin/status` gains `fit`: the context served, the model's own, the parallel requests asked and served, where the context came from (`settings`, `cache` or `search`), the loads, the model's digest, and `size` and `size_vram`. `open-key` logs it: "Pod … serves … with 4 parallel requests and a context of 131072 tokens (the model's own is 262144), wholly on the GPU; found in 5 loads." Its `context-length` output, which the agent is told, is the context served, as today.

## End-to-end test

By the responsible person, on the test repository, after pushing. Its settings: a profile with `tasks: 4` on `NVIDIA RTX PRO 6000 Blackwell Server Edition` and one with `max-tasks: 3` on `NVIDIA RTX PRO 6000 Blackwell Server Edition MIG 2g.48gb`, both with `qwen3.8:27b-mtp-q4_K_M`, without `ollama:`. Costs are estimates, with the full GPU at about US$ 2 an hour and the MIG partition at about US$ 1; check Runpod's prices.

1. **Before pinning, nothing changes.** With the pinned image, run a task on a pod. `open-key`'s log says the derived `num-parallel` and the computed context do not apply to the image; the pod's environment has no `CODEMAN_OLLAMA`, `CODEMAN_FIT` nor `CODEMAN_GPU_MEMORY_GB`; the pod serves as before. Cost: one run, as usual.
2. **Publish and pin the image.** Push; the pod image workflow publishes `ghcr.io/codenergy-dev/codeman-pod` from the new `dist/gateway.js`. Send its digest; it is pinned in `POD_IMAGE` in a commit of its own, and the image pinned now stays in `IMAGES_WITHOUT_OLLAMA_SETTINGS`. This one image covers the Ollama settings plan too. Cost: none.
3. **The family.** In the first pod's log, or with `ollama show`, read the model's family. If it is one Ollama serves one request at a time (`qwen35` and the others of choice 11), `open-key` warns so, and the 4 tasks queue on the pod: then the profile's count buys no speed on one pod, and the responsible person decides whether to keep it. Cost: none beyond step 4.
4. **Four tasks on the full GPU.** With 4 tasks ready past planning, start a run. Check: the pod's `CODEMAN_OLLAMA` has `OLLAMA_NUM_PARALLEL=4` (and no context length) and its environment `CODEMAN_GPU_MEMORY_GB=96`; the gateway's log shows the estimate and each load with its context and whether it was wholly on the GPU; `open-key` logs the context served, which is at least 64000 and a multiple of 4096 or the model's own, and the loads; `open-key`'s `context-length` output and OpenCode's configuration have it; Firestore has a document in `organizations/<owner>/contexts/` with that context and the model's digest; Ollama's log shows no layers on the CPU. Cost: about 20 to 40 minutes of the full GPU, the search a few of them, around US$ 1 to 1.50.
5. **The cache.** Once the pod of step 4 has ended, start another run of 4 tasks. The new pod's environment has `CODEMAN_FIT` with the context of step 4; the gateway loads once, with it, and `open-key` reports it from the cache. Cost: as step 4, without the search's minutes.
6. **Three tasks on the MIG partition.** With 2 or 3 tasks ready, start a run. `OLLAMA_NUM_PARALLEL=3`, `CODEMAN_GPU_MEMORY_GB=48`, a context computed for them, and a cache document of its own (another GPU type). If even 64000 tokens do not fit 3 requests in 48 GB, the run fails with the floor's message and the pod is terminated within minutes; then try `kv-cache-type: q8_0` in the profile's `ollama:`, which gets a cache document of its own. Cost: about 10 to 20 minutes of the partition, under US$ 0.50.
7. **An explicit context that does not fit.** In the full-GPU profile, set `ollama:` with `context-length: 262144`. A run fails with the explicit context's message, naming 4 requests and 262144 tokens, and the pod is terminated; no cache document is written. Remove it. Cost: one pod's start and a load, about 5 to 10 minutes, under US$ 0.40.

## Out of scope

- Searching above a context that fits: a start that fits is kept (decision 3).
- Several GPUs per pod: pods have one GPU.
- Lowering `num-parallel` to fit the floor: the start fails and says so.
- Refreshing a cache document when nothing failed, such as after a driver's change; a cached context that no longer fits is searched again and replaced.
- vLLM and Serverless endpoints.
